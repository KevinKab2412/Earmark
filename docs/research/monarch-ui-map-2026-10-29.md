# Monarch UI map for Earmark

**Updated:** 2026-11-01 (initial live capture 2026-10-29)
**Sources:** Fresh Mobbin web and mobile searches (Nov 1, 2026), Monarch Help Center, live October/November 2026 Monarch web UI, and the two user-provided screenshots.

This is an interaction map, not a pixel-perfect specification. No Monarch MCP was available. An authenticated Chrome session was used to inspect the live Dashboard, Accounts, Transactions, Budget, Goals, Categories settings, account import entry point, and several small controls; account names, balances, and transaction details are omitted. Mobbin flows show sampled screens, not every intermediate state. The two user screenshots are visual evidence for Earmark’s category setup and move-budget affordance; product decisions come from the user’s written direction. Unverified details are called out explicitly.

## Proposed Earmark data model for discussion

This is the proposed translation of the behavior decisions already made in the conversation. The relationship and cardinality choices below reflect the user's answers and are ready for a focused data-model review before more model changes.

| Record | Responsibility |
|---|---|
| Category group | A named, ordered container for categories with one direction: income, expense, or transfer. Direction is persisted on the group; each category's queryable direction mirrors its group. It has no planned amount or budget balance. |
| Category | The sole budget unit. It must belong to a direction-specific group and inherits that direction. It has a starting month, opening balance in cents, and month-effective rollover settings. Rollover is Expense-only and carries either sign. A savings goal owns one dedicated Expense category and enables rollover when linked. Transaction and split goal attribution follows category; there is no separate goal link. Balance Adjustments is a non-budgetable special kind inside Transfers. |
| Category budget plan | A month-effective planned amount. An edit can apply to the selected month or replace that month and later plan entries. |
| Rollover setting | A month-effective category setting. When enabled, the full positive or negative available balance carries into the next month. |
| Category budget move | A separate month-specific record with source and destination category, amount, memo, and author. It rebalances available funds without rewriting either category's planned amount. Groups are never endpoints. |
| Transaction | An account movement assigned to one category, or split across categories. Purchases remain expenses even when paid by credit card. A Transfer-category row is excluded from income, expense, and category budgets by its category direction even before it has a confirmed counterpart. |
| Transfer pair | A confirmed relationship between two opposite-signed account transactions. The pair ID links counterpart rows; the Transfer category direction is what excludes either row from income, expense, and category budgets, including an unpaired row. Deleting one side removes the relationship and preserves the other as an unpaired transaction. |
| Transfer import match | A suggested counterpart remains unpaired until the user confirms it. Exact amount, opposite sign, different account, and a three-day date window are proposed matching heuristics, not confirmed product rules. |
| Goal | A savings goal reads its dedicated expense category's available balance and enables rollover when linked; only one active savings goal may use a category. Transactions and splits affect goal progress through that category. A debt goal reads one linked liability account or position, never both, and may reference an optional standard Expense or Transfer payment category. An Expense payment category remains budget spending; a Transfer payment category is excluded from spending, which supports credit-card payments without double-counting. |
| Statement upload | Keep the source file and staged rows through mapping, validation, duplicate review, transfer-match suggestions, and explicit import confirmation. Existing Bucket plans and assignments are not converted; the household starts with clean category/group defaults. |

The user has confirmed the category-first budget, direction-specific groups, opening month/balance, expense-only rollover carrying either sign, per-edit future-month choice, category-based savings goals with transaction/split attribution derived from category, separate move records that can cross income/expense directions, transfer suggestions with confirmation, and pair-preserving deletion behavior. Balance Adjustments stays a special non-budgetable category inside Transfers. The three-day transfer candidate window remains a proposed Earmark heuristic, not a Monarch rule.

| Move endpoints | The request accepts income or expense categories on either side, so cross-direction moves are supported; both endpoints must belong to the household and differ. The month-specific move stores source, destination, amount, memo, and author. | This matches the separate move record decision. | Plans, rollover, and moves | Plans and rollover settings are category/effective-month records; moves are separate records. Starting month and opening balance are fields on Category. The budget service computes opening balance + carryover + plan + moves in − moves out + signed transaction/split activity; the previous available balance carries forward only when the previous month had rollover enabled. | Keep the starting month and opening balance on Category for this fresh start. Keep plans, rollover settings, and moves as effective-month records so later changes do not rewrite earlier months. |
| Savings goals | Save-up request validation requires a standard Expense category; a partial unique database index allows only one active save-up goal per category. The controller enables rollover for the linked category. Debt goals link to exactly one liability account or position. | Savings progress reads the dedicated category balance. Debt progress reads the selected liability balance; its optional payment category can be standard Expense or Transfer. Neither goal aggregates multiple categories or liabilities. |
| Debt payment category | Main validation accepts standard Expense or Transfer categories and excludes the special Balance Adjustments category. The payment category is stored and displayed but does not drive debt-balance calculation, which reads the one linked liability. | A Transfer payment category supports credit-card payment tracking without counting the payment as spending; Expense remains available for other debt payment flows. |
| Transfer deletion | Transactions share a `transfer_pair_id`. Deleting one side clears the sibling’s pair ID and preserves that transaction; `TransfersPageTest` covers this behavior. Both legs are stored as separate account transactions. The schema does not constrain a pair ID to exactly two rows. | Keep the shared ID: confirmed matches exist in staged review before both rows are ledger transactions, so a transactions-only pair table would complicate promotion. Enforce exactly two eligible legs in domain actions. Add a pair table only if pair-owned metadata or database-level cardinality becomes necessary. |

## Current Goals reference and transaction attribution

Monarch's current Goals experience was announced June 23, 2026, after the 2025 Mobbin goal flows above. Its official overview describes savings status as a function of current balance, planned monthly contributions, and target date; account balances can be assigned many-to-many across goals; and each goal can choose whether spending reduces progress. See [Goals, reimagined](https://www.monarch.com/blog/goals).

| Reference | Current Monarch behavior | Earmark model impact |
|---|---|---|
| [Web transaction detail](https://mobbin.com/screens/e75d351a-b5cc-42e5-a134-79688e30f988) | Category and Goal are separate fields. | A transaction can be assigned to a goal independently of its budget category. |
| [Web split transaction dialog](https://mobbin.com/screens/6610f917-eb60-4b86-8345-70789d15038e) | Each split row has its own Link to goal field. | Explicit attribution can apply at split level, not just the whole transaction. |
| [Goals, reimagined](https://www.monarch.com/blog/goals) | Goal spending can reduce progress or be excluded, by goal choice; goals are included in the monthly budget. | A dedicated category alone cannot represent Monarch's per-goal spending exception if all progress must equal category available balance. |

| Earmark option | Data relationship | Consequence |
|---|---|---|
| Category-derived goal (selected by the user) | A savings Goal owns one dedicated expense Category; transactions and splits affect it only through their category. No transaction `goal_id`. | Category available balance stays the single source of truth. There is no separate per-transaction spending-exclusion setting. |
| Explicit goal attribution | Transactions and individual splits can link to a Goal independently from Category. | Supports Monarch's separate contribution/spending attribution and spending-exclusion behavior, but requires a rule for reconciling those events with category balance. |

The Mobbin web screenshots expose Goal attribution directly; Mobbin provides no capture date for these screens. The official Goals overview is dated June 23, 2026 and reflects the newer experience. Earmark intentionally keeps the user's category-derived progress model rather than adding Monarch's independent goal-spending attribution.
